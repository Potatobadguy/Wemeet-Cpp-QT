# WeMeet v2.1 优化与屏幕共享完善 PRD

- **Language**: 中文
- **Programming Language**: C++17 / Qt6（既有技术栈，信令服务器 + SFU 媒体中继 + Qt 客户端）
- **Project Name**: wemeet_optimize
- **原始需求复述**：对 WeMeet v2.0 代码审查发现的 18 个优化点进行修复（P0 死锁/线程安全、P1 性能瓶颈、P2 代码质量、P3 工程实践），同时参考主流会议软件完善屏幕共享功能（共享源选择、帧率/质量自适应、暂停/恢复、性能优化），控制代码量在个人项目合理范围内。

---

## 1. 产品定义

### 1.1 Product Goals

修复 v2.0 中影响系统稳定性的致命缺陷（递归死锁、多线程不安全调用），消除媒体转发热路径上的性能瓶颈，提升代码质量与工程规范性；同时将屏幕共享从"基础可用"完善到"体验良好"，使其具备主流会议软件的核心共享能力（源选择、暂停/恢复、自适应质量），保持个人项目代码规模可控。

### 1.2 User Stories

1. 作为**会议参与者**，我希望媒体服务器在高并发下不会因死锁或数据竞争崩溃，以便会议能稳定进行数小时不中断。
2. 作为**会议主持人**，我希望共享屏幕时能选择共享整个屏幕还是某个特定窗口，以便避免泄露无关隐私内容（如聊天消息、通知）。
3. 作为**屏幕共享发起者**，我希望在需要时能一键暂停共享（画面冻结）并在稍后恢复，以便我临时处理私密操作而不必中断共享流程。
4. 作为**网络条件较差的观看者**，我希望屏幕共享能根据网络状况自动调整帧率和画质，以便画面流畅不卡顿。
5. 作为**项目维护者**，我希望消除热路径上的性能浪费（逐包全量扫描、深拷贝、地址转换）和代码坏味道（重复定义、硬编码密码、死代码），以便系统易维护、可扩展。

## 2. 技术规范

### 2.1 Requirements Pool

> 优先级定义：P0 = 必须完成（正确性/安全）；P1 = 应当完成（性能/核心体验）；P2 = 最好完成（质量/增强体验）；P3 = 可选（工程规范）。

#### A. 缺陷修复与优化（来自代码审查）

| # | 优先级 | 需求 | 说明 / 验收标准 |
|---|--------|------|----------------|
| 1 | **P0** | 修复 media_relay.cpp 递归死锁 | report_stats() 持 rooms_mutex_ 调用 suggest_bitrate() 重入同一非递归 mutex。方案：拆分锁粒度或提供不加锁的私有版本（`_locked` 后缀约定）。修复后压测 stats 上报路径无死锁 |
| 2 | **P0** | 消除 inet_ntoa 多线程不安全 | inet_ntoa 返回静态缓冲区。替换为 inet_ntop() + 线程局部/栈上缓冲区，覆盖所有 relay 工作线程调用点 |
| 3 | **P1** | SSRC 反查性能优化 | 每个 RTP 包 O(rooms×participants×streams) 全量扫描 → 建立 `ssrc → (room, participant, stream)` 的哈希索引（unordered_map），注册/注销流时维护，反查降为 O(1) |
| 4 | **P1** | 移除逐包参与者深拷贝 | get_room_participants() 返回值未使用却每包深拷贝。删除该调用或改为只读引用/计数接口 |
| 5 | **P1** | 预解析目标地址 | inet_pton 逐包逐目标字符串转地址 → 参与者加入时预存 `sockaddr_in`，转发时直接使用 |
| 6 | **P1** | EventLoop 回调表去锁 | 单线程 EventLoop 每个 epoll 事件经 mutex 查 fd 回调表 → 确认单线程语义后移除锁（或文档化线程模型） |
| 7 | **P1** | SPSCQueue 自旋退避 | 自旋等待加入 `_mm_pause()`（或 std::this_thread::yield 兜底），降低空转 CPU 占用 |
| 8 | **P2** | 实现 cancel_timer | 当前空实现导致 timerfd 泄漏。实现按 timer id 关闭/回收 timerfd，补充单元测试 |
| 9 | **P2** | 消除 RTPHeader 重复定义 | server/client 两处重复定义 → 抽取到公共头文件（如 proto/ 或 common/），保持二进制布局一致（packed 属性验证） |
| 10 | **P2** | 修复 idle_count() 数据竞争 | ConnectionPool::idle_count() 无锁读 → 加锁或使用 atomic 计数 |
| 11 | **P2** | 移除 RTCPReportBlock 位域死代码 | 位域不应用于网络协议（字节序不可移植），若为死代码则删除，若在用则改为显式字节序转换 |
| 12 | **P2** | SSRC 随机化分配 | 顺序分配可预测 → 改用随机 SSRC（冲突时重试），符合 RFC 3550 建议 |
| 13 | **P2** | relay_sockets_ 停止时线程安全 | stop() 中无锁访问 → 加锁保护或使用原子标志 +  join 前同步 |
| 14 | **P2** | 移除硬编码默认密码 | db_pass 默认 "123456" → 改为必须从配置/环境变量读取，缺省启动失败并提示 |
| 15 | **P3** | MemoryPool 改用侵入式链表 | vector 管理空闲链表有额外分配开销 → 空闲块内嵌 next 指针的侵入式 freelist |
| 16 | **P3** | Logger 编译期格式检查 | 变参格式化 → 改用 C++20 std::format 或 fmt 库（带编译期格式串检查） |
| 17 | **P3** | RTP 包完整校验 | 增加版本号、负载类型、包长、SSRC 合法性校验，非法包丢弃并计数 |
| 18 | **P3** | relay 线程函数静态变量重构 | static 局部变量移为类成员，消除隐藏共享状态 |

#### B. 屏幕共享完善

| # | 优先级 | 需求 | 说明 / 验收标准 |
|---|--------|------|----------------|
| 19 | **P0** | 共享源选择 | 发起共享前弹出选择对话框：支持「整个屏幕」（多屏时可选屏幕）和「应用窗口」（枚举可见窗口列表，含缩略图/图标+标题）。选中后方可开始共享 |
| 20 | **P0** | 暂停 / 恢复共享 | 共享工具栏提供暂停按钮：暂停时停止抓帧，向对端发送冻结标志（或最后一帧+静态提示），恢复后继续推流。UI 状态清晰可辨 |
| 21 | **P1** | 帧率/质量自适应 | 根据发送码率与 RTCP 反馈（丢包率）动态调节：抓帧帧率（如 5/10/15 fps 档位）与 JPEG 质量（如 40/60/80 档位）。网络好升档、差降档，调整过程对码率平滑 |
| 22 | **P1** | 抓帧性能优化 | 降低抓帧开销：仅画面变化时编码发送（帧差检测/脏区域），或降低静止时帧率（如静止 1-2 fps）。CPU 占用较当前实现明显下降 |
| 23 | **P2** | 共享中状态指示 | 本地显示明显的"共享中"标识（浮动工具条/边框高亮），含停止、暂停按钮，防止用户忘记自己正在共享 |
| 24 | **P2** | 窗口跟随与源失效处理 | 被共享窗口关闭/最小化时给出提示并优雅降级（暂停或提示重新选择源），而非发送黑屏 |

### 2.2 UI Design Draft（屏幕共享）

#### 共享源选择对话框（ShareSourceDialog）

```
┌─────────────────────────────────────────────┐
│  选择共享内容                              ✕ │
├─────────────────────────────────────────────┤
│  [ 屏幕 ] [ 应用窗口 ]     ← Tab 切换        │
│ ┌──────────┐ ┌──────────┐ ┌──────────┐      │
│ │ 屏幕 1   │ │ 屏幕 2   │ │          │      │  ← 缩略图网格，
│ │ (缩略图) │ │ (缩略图) │ │          │      │    窗口 Tab 显示
│ └──────────┘ └──────────┘ └──────────┘      │    窗口图标+标题
│ ┌──────────┐ ┌──────────┐                   │
│ │ 编辑器   │ │ 浏览器   │                   │
│ └──────────┘ └──────────┘                   │
├─────────────────────────────────────────────┤
│  ☐ 同时共享电脑声音（P2 可选，默认隐藏）      │
│                        [ 取消 ] [ 开始共享 ] │
└─────────────────────────────────────────────┘
```

- **布局**：模态对话框，约 640×480；顶部两个 Tab（屏幕 / 应用窗口）；中部为 3 列缩略图网格，每项为实时缩略图（屏幕用 QScreen::grabWindow 缩略，窗口用其图标+标题快照）；底部为操作按钮。
- **交互**：单击选中某项（蓝色高亮边框）→「开始共享」按钮由灰变可用；双击直接选中并开始。「取消」关闭对话框返回会议。
- **共享中浮动工具条**（屏幕顶部居中，可拖动）：

```
┌──────────────────────────────────────────┐
│ ● 正在共享屏幕  [⏸ 暂停] [■ 停止共享] [—] │
└──────────────────────────────────────────┘
```

- 暂停时「● 正在共享」变为「‖ 已暂停」，暂停按钮变为「▶ 恢复」；最小化（—）收起为一条细条。
- **观看端**：共享画面区域右上角显示共享者名称与「屏幕共享」标识；共享暂停时画面中央叠加半透明提示「对方已暂停共享」。

### 2.3 Open Questions（待确认问题）

1. **窗口枚举的跨平台范围**：Qt 枚举第三方应用窗口在 Windows 上需 Win32 API（EnumWindows），Linux 需 X11/Wayland 处理。本期是否仅支持 Windows？还是窗口级共享仅支持枚举本进程窗口（纯 Qt 可实现）？
2. **帧差检测的精度**：P1 的"仅画面变化时编码"采用整帧像素对比（简单、CPU 有开销）还是分块脏矩形（复杂、更高效）？建议先用整帧对比 + 静止降帧，脏矩形留作后续优化，是否认可？
3. **自适应调节的指标来源**：码率/丢包反馈依赖 RTCP RR，当前 RTCP 实现是否已具备可用的丢包率统计？若无，P1 自适应是否降级为手动档位切换？
4. **音频共享**：主流软件支持"共享电脑声音"，但涉及音频捕获链路，工作量较大。本期是否明确排除（P2 甚至不做）？
5. **P3 项的取舍**：Logger 改用 fmt 会引入第三方依赖，是否与项目"零外部依赖/学习导向"的约束冲突？MemoryPool 侵入式链表重构的收益是否值得在本期投入？
6. **兼容性**：RTPHeader 抽取公共头后，需确保 server/client 结构体打包方式（#pragma pack / attribute packed）一致，是否需要同步更新协议文档与单元测试？
