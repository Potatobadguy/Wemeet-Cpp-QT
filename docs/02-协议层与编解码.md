## 1. 为什么用 Protobuf 而不是 JSON

| 对比维度 | JSON | Protobuf |
|----------|------|----------|
| 格式 | 文本（人类可读） | 二进制（机器高效） |
| 体积 | 大（含字段名、引号、括号） | 小（仅存字段编号+值） |
| 解析速度 | 慢（需解析字符串） | 快（直接读二进制偏移） |
| 类型安全 | 无（全靠约定） | 强（`.proto` 定义即文档） |
| 适用场景 | Web API、配置文件 | 高性能网络通信、存储 |

**举例**：同一份用户数据，JSON 约 80 字节，Protobuf 约 20 字节，体积缩小 75%。

## 2. 协议设计模式：BaseMessage 包裹

### 核心思想

```
BaseMessage {                        ← 外层信封
  type: 100                          ← 消息类型（谁处理）
  sequence_id: 42                    ← 请求响应匹配（哪个请求的回复）
  timestamp_ms: 1690000000000        ← 时间戳
  payload: <二进制>                  ← 内层消息序列化后的二进制
}
         │
         └── 根据 type 反序列化为:
              LoginReq / RegisterReq / SDPOffer ...
```

**为什么这样设计**：
- **type** 让服务端拿到消息就知道用哪个 handler
- **sequence_id** 客户端发请求时自增，服务端原样返回，客户端据此匹配"这个响应对应哪个请求"（类似 HTTP/2 的 stream id）
- **payload** 是 `bytes` 类型，可以塞任何序列化后的子消息，实现协议扩展（加新消息类型只需加新的 case，不影响已有逻辑）

### `common.proto` — 基础定义

```protobuf
enum MsgType {
    // 100-199: 登录注册
    MSG_LOGIN_REQ = 100;    MSG_LOGIN_RESP = 101;
    MSG_REGISTER_REQ = 102; MSG_REGISTER_RESP = 103;
    // 200-299: 心跳/保活
    MSG_HEARTBEAT_REQ = 200; MSG_HEARTBEAT_RESP = 201;
    // 300-399: 好友
    MSG_FRIEND_LIST_REQ = 300; ...
    // 400-499: 会议
    MSG_MEETING_CREATE_REQ = 400; ...
    // 500-599: 信令
    MSG_SDP_OFFER = 500; ...
    // 600-699: 聊天
    MSG_CHAT_SEND = 600; ...
    // 900-999: 错误
    MSG_ERROR = 999;
}
```

**编号分段的约定**：按功能模块分段，每个模块预留 100 个号，方便扩展。

## 3. Codec — Protobuf 编解码器

**文件**：`src/network/codec.h`（72行，纯头文件实现）

### 自定义帧格式

```
┌──────────────┬─────────────────────────┐
│   4 bytes    │    N bytes               │
│   大端序     │    Protobuf 序列化数据    │
│   body 长度  │    (BaseMessage)         │
└──────────────┴─────────────────────────┘
```

### 为什么需要长度头

**TCP 粘包/拆包问题**：

```
发送方两次 write:
  write("Hello")  →  5 bytes
  write("World")  →  5 bytes

接收方可能一次 read 到:
  "HelloWorld"       ← 粘包：两条消息粘在一起
  "Hel"               ← 拆包：一条消息分成多次到达
  "loWorld"
```

**长度头解决方案**：
1. 先读 4 字节 → 知道 body 长度 N
2. 再读 N 字节 → 完整一条消息
3. 重复...

这叫做 **TLV（Type-Length-Value）模式的简化版**。

### C++ 技术点详解

#### 3.1 网络字节序 `htonl` / `ntohl`

```cpp
uint32_t net_len = htonl(body.size());   // host → network (x86小端 → 大端)
// ...
uint32_t len = ntohl(*(uint32_t*)buf.peek());  // network → host (大端 → x86小端)
```

不同 CPU 架构存储多字节整数的方式不同：
- **小端（x86）**：低位字节在低地址
- **大端（网络标准）**：高位字节在低地址

`htonl`（Host TO Network Long）保证跨平台兼容。

#### 3.2 模板编码 `encode_wrapped`

```cpp
template <typename InnerMsg>
static Buffer encode_wrapped(int msg_type, uint64_t seq_id, const InnerMsg& inner) {
    BaseMessage base;
    base.set_type(static_cast<MsgType>(msg_type));
    base.set_sequence_id(seq_id);
    base.set_timestamp_ms(/* 当前毫秒时间戳 */);
    base.set_payload(inner.SerializeAsString());   // 子消息 → 二进制 → 塞入 payload
    return encode(base);                            // BaseMessage → 二进制 → 加长度头
}
```

模板函数让调用方只需传具体消息类型，编译器自动推导：

```cpp
LoginResp resp;
auto buf = Codec::encode_wrapped(MSG_LOGIN_RESP, seq_id, resp);
// 编译器自动实例化为 Codec::encode_wrapped<LoginResp>(...)
```

#### 3.3 解码

```cpp
// 第一步：从 buffer 解码出 BaseMessage
BaseMessage base;
Codec::decode_base_message(buf, base);

// 第二步：根据 type 从 payload 中解码出具体消息
LoginReq req;
Codec::decode_payload(base, req);
```

两步解码对应两步编码（子消息序列化→塞入BaseMessage→BaseMessage序列化），完全对称。
