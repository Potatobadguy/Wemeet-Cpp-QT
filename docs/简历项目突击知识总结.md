## 一、Reactor + epoll ET 事件循环

### 核心代码 (`src/network/event_loop.cpp:42-110`)

```cpp
void EventLoop::loop() {
    running_ = true;
    while (!quit_) {
        int ready = ::epoll_wait(epoll_fd_, events_.data(), kMaxEvents, kEpollTimeoutMs);
        for (int i = 0; i < ready; ++i) {
            int fd = events_[i].data.fd;
            uint32_t ev = events_[i].events;

            if (fd == wakeup_fd_) {             // eventfd 唤醒
                read(wakeup_fd_, &val, sizeof(val));
                process_pending_tasks();         // 处理跨线程投递的任务
                continue;
            }
            if (ev & EPOLLIN)  fd_read_callbacks_[fd]();   // 可读 → 回调
            if (ev & EPOLLOUT) fd_read_callbacks_[fd]();   // 可写 → 回调
        }
    }
}
```

### 为什么用 epoll ET（边缘触发）不用 select/poll？

| 对比项 | select | poll | epoll (ET) |
|--------|--------|------|------------|
| 时间复杂度 | O(n) 遍历全部 fd | O(n) | **O(1)** 只返回就绪 fd |
| fd 上限 | 1024 | 无限制 | 无限制 |
| 触发模式 | 水平触发（LT） | LT | 可设 **ET** — 只通知一次，必须一次读完 |
| 数据拷贝 | 每次传入全部 fd_set | 全部 fd | **mmap 共享内存**，零拷贝 |

**不用会怎样**：C10K（1 万并发连接）场景下，select/poll 每次都要把全部 fd 从用户态拷贝到内核态、内核再线性扫描一遍——内核时间复杂度 O(n)，服务器会随着连接数增加而线性变慢。epoll ET + O(1) 就绪回调能支撑 C10K。

### ET 边缘触发为什么配非阻塞 I/O？

```cpp
// event_loop.cpp:131-137
void EventLoop::enable_write(int fd) {
    update_channel(fd, EPOLLIN | EPOLLOUT | EPOLLET);
}
```

ET 模式下，一个事件**只通知一次**，必须把数据**全部读完**（`read` 到返回 `EAGAIN`）或**全部写完**（`write` 到返回 `EAGAIN`），否则剩余数据不会再触发通知。因此 socket 必须设 `O_NONBLOCK`，配合 `while(read() > 0)` 循环读尽。

### 输入/输出

| | 数据 | 来源/去向 |
|--|------|----------|
| **输入** | `epoll_wait()` 返回的 ready fd 集合 | Linux 内核，来自客户端 TCP 连接的数据到达 |
| **输出** | 通过回调函数（`ReadCallback`）分发给注册的 handler | `TcpConnection::handle_read()` 读取数据 → `Buffer` |

## 二、wakeup_fd (eventfd) + 跨线程任务投递

### 核心代码 (`event_loop.cpp:237-259`)

```cpp
// 从其他线程投递任务到本 loop
void EventLoop::run_in_loop(std::function<void()> task) {
    {
        std::lock_guard<std::mutex> lock(pending_mutex_);
        pending_tasks_.push_back(std::move(task));
    }
    wakeup();
}

void EventLoop::wakeup() {
    uint64_t val = 1;
    ::write(wakeup_fd_, &val, sizeof(val));  // 写入 eventfd 唤醒 epoll_wait
}
```

### 为什么需要 wakeup_fd？

`epoll_wait` 是**阻塞**的。如果线程 A 要给线程 B 的 EventLoop 投递一个任务（比如发数据），直接写线程 B 的 `pending_tasks_` 队列还不够——B 正卡在 `epoll_wait` 上不返回。往 B 的 `wakeup_fd_`（eventfd）写 1 字节，epoll 立即返回，`process_pending_tasks()` 被执行。

**不用会怎样**：跨线程任务延迟不可控——必须等 `epoll_wait` 超时（默认 10 秒）才能执行，导致心跳超时、断线重连卡顿。

### 输入/输出

| | 数据 | 来源/去向 |
|--|------|----------|
| **输入** | `std::function<void()>` 可调用对象 | 调用者线程（如 TcpConnection 的 `send_in_loop`） |
| **输出** | 任务在目标 EventLoop 线程同步执行 | 写到 `pending_tasks_`，`process_pending_tasks()` 按序消费 |

## 三、timerfd 高精度定时器

### 核心代码 (`event_loop.cpp:160-235`)

```cpp
int EventLoop::run_every(int64_t interval_ms, TimerCallback cb) {
    int timer_fd = ::timerfd_create(CLOCK_MONOTONIC, TFD_NONBLOCK | TFD_CLOEXEC);

    struct itimerspec its{};
    its.it_value.tv_sec     = interval_ms / 1000;
    its.it_value.tv_nsec    = (interval_ms % 1000) * 1000000;
    its.it_interval.tv_sec  = interval_ms / 1000;   // 重复间隔
    its.it_interval.tv_nsec = (interval_ms % 1000) * 1000000;

    ::timerfd_settime(timer_fd, 0, &its, nullptr);
    update_channel(timer_fd, EPOLLIN | EPOLLET);     // 注册到 epoll
    // ...
}
```

### 为什么用 timerfd 不用 `setitimer` / `sleep`？

- timerfd 是**文件描述符**，可以直接挂在 epoll 上，和网络 I/O 统一事件驱动
- `setitimer` 发信号（`SIGALRM`），多线程下信号处理复杂
- `sleep` 会阻塞线程，完全不能用于 Reactor 模式
- 精度：timerfd 支持**纳秒级**，`sleep` 只有毫秒级

**不用会怎样**：定时器要么阻塞线程（sleep）、要么信号处理竞态（setitimer），无法融入 Reactor 事件循环的统一调度。

## 四、One Loop Per Thread + EventLoopPool

### 核心代码 (`src/network/event_loop_pool.cpp:6-53`)

```cpp
EventLoopPool::EventLoopPool(size_t num_loops) {
    if (num_loops == 0) num_loops = std::thread::hardware_concurrency();  // 自动检测 CPU 核数

    main_loop_ = std::make_unique<EventLoop>();  // 主 Reactor：accept
    for (size_t i = 0; i < num_loops; ++i) {
        loops_.push_back(std::make_unique<EventLoop>());  // 子 Reactor：I/O 读写
    }
}

void EventLoopPool::start() {
    for (size_t i = 0; i < loops_.size(); ++i) {
        threads_.emplace_back([this, i]() { loops_[i]->loop(); });
    }
}

EventLoop* EventLoopPool::next_loop() {
    size_t idx = next_index_.fetch_add(1, std::memory_order_relaxed) % loops_.size();
    return loops_[idx].get();   // Round-Robin 分发新连接
}
```

`TcpServer` 用它分发连接：

```cpp
// tcp_server.cpp:66
EventLoop* io_loop = pool_->next_loop();  // 轮询选一个 worker
auto conn = std::make_shared<TcpConnection>(io_loop, ...);  // 连接注册到该 worker
```

### 架构图

```
主 Reactor (EventLoop 1):
  监听 socket → accept() → 分发给子 Reactor

子 Reactor (EventLoop 2..N):
  epoll_wait 自己的 fd 集合:
    - TcpConnection A 的 socket
    - TcpConnection B 的 socket
    - ...
  每个线程独立 loop，互不干扰
```

### 为什么不用单线程 Reactor？

单线程 Reactor 的问题：一个慢操作（比如解包 1MB 的 Protobuf 消息）会阻塞整个事件循环，**所有连接都卡住**——即使 CPU 还有大量空闲核心。

One Loop Per Thread = 每个 CPU 核一个事件循环，连接按 Round-Robin 分到不同线程。其中一条连接上的慢操作只阻塞它所在的 worker，不影响其他 worker 上的连接。

**不用会怎样**：1000 个连接中只要有一个发大消息，所有 999 个连接都得等它处理完，CPU 多核完全浪费。

### 输入/输出

| | 数据 | 来源/去向 |
|--|------|----------|
| **输入** | accept 的新连接 Socket | `TcpServer::handle_accept()` 从 `listen_sock_` accept |
| **输出** | 分配到子 Reactor 的 `TcpConnection` | `pool_->next_loop()` → `conn->start()` 注册到该 loop 的 epoll |

## 五、TcpServer + TcpConnection（连接生命周期管理）

### 核心代码 (`tcp_server.cpp:55-95`)

```cpp
void TcpServer::handle_accept(Socket conn_sock, const sockaddr_in& peer_addr) {
    uint64_t conn_id = next_conn_id_.fetch_add(1);  // 全局递增 ID
    EventLoop* io_loop = pool_->next_loop();          // 分配到 worker

    auto conn = std::make_shared<TcpConnection>(io_loop, std::move(conn_sock), conn_id);

    conn->set_close_callback([this](const std::shared_ptr<TcpConnection>& closed_conn) {
        uint64_t id = closed_conn->conn_id();
        shards_[id % kShardCount].connections.erase(id);  // 从分片表移除
    });

    shards_[conn_id % kShardCount].connections[conn_id] = conn;  // 存入 16 分片表
    conn->start();
}
```

### 为什么用 16 分片连接表 + `shared_ptr`？

**16 分片**：连接表是 `std::map<uint64_t, shared_ptr<TcpConnection>>`，散列到 16 个 `Shard`。每个 Shard 有独立的 `mutex`。多个线程同时查/写不同分片时**不竞争锁**── 写入时只锁一个分片，其他 15 个分片的读写完全不受影响。

**`shared_ptr`**：`TcpConnection` 继承 `enable_shared_from_this`（`tcp_connection.h:24`）。所有 epoll 回调 lambda 都 `[self = shared_from_this()]` 捕获一份引用。这样即使上层业务（`SignalingServer::on_message`）内触发了 close + 从连接表 erase，只要还有正在执行的 lambda 持有 `self`，对象就不会析构。

```cpp
// tcp_connection.cpp:25-26
void TcpConnection::start() {
    auto self = shared_from_this();
    loop_->add_read_event(sock_.fd(), [self]() {
        self->handle_read();
    });
}
```

**不用会怎样**：
1. 裸指针 → close 回调从 map erase 后对象析构，但 `handle_read` 还在执行 → **use-after-free 段错误**
2. 单表 + 全局锁 → 几十个连接同时读写，锁竞争把 CPU 时间都消耗在等待上

### 输入/输出

| | 数据 | 来源/去向 |
|--|------|----------|
| **输入** | 新 TCP 连接（监听 socket accept 得来） | 客户端 `QTcpSocket::connectToHost` |
| **输出** | `TcpConnection::start()` → 注册到 EventLoop | `loop_->add_read_event(fd, callback)` → epoll 监听 fd |

Buffer Codec::encode(const MsgType& msg) {

### Buffer 的移动语义（`buffer.h:37-58`）

```cpp
Buffer(Buffer&& other) noexcept
    : buffer_(std::move(other.buffer_))  // vector 的移动 → 只转移指针
    , read_idx_(other.read_idx_)
    , write_idx_(other.write_idx_) { }

Buffer(const Buffer&) = delete;  // 禁止拷贝
```

音视频帧从网络线程 → 业务线程传递时，`Buffer` 通过 `std::move` 只转移底层 `vector` 的所有权（三个指针），**不复制任何字节**。拷贝构造被 delete，编译期就能阻止意外深拷贝。

### 为什么用长度头 + 变长体，而不是定长协议？

TCP 是**流式传输**，没有消息边界。定长协议（比如固定 64 字节一条）处理简单，但 Protobuf 序列化后长度不固定——定长太短装不下会议列表、太长浪费带宽。长度头方案：先读 4 字节知道 body 有多长，再等刚好 `body_len` 个字节，既能处理**粘包**（一次 recv 收到多条完整消息），也能处理**半包**（一条消息分多次 recv 到达）。

**不用会怎样**：无法准确区分"一条消息结束"和"下一条消息开始"，要么数据错位（帧尾被当成新帧头），要么用 `\n` 分割（body 里不能有换行符）。

| | 数据 | 来源/去向 |
|--|------|----------|
| **输入** | 原始字节流（来自 `::read(sock_fd)`） | TCP 缓冲区，客户端发送的 Protobuf 消息 |
| **输出** | `BaseMessage{type, seq_id, payload}` | 送 `SignalingServer::on_message()` switch 分发 |

## 七、SFU 媒体中继

### 核心代码 (`media_relay.cpp` 关键流程)

```cpp
struct RTPHeader {           // 标准 RTP v2，12 字节
    uint8_t  cc_version;     // [4:7] version=2
    uint8_t  pt_marker;      // [0:6] payload type
    uint16_t sequence_number;
    uint32_t timestamp;
    uint32_t ssrc;           // 同步源标识——用于识别发送者
};

// 注册参与者时，同一用户复用同一个 SSRC
if (!p->streams.empty()) {
    out_ssrc = p->streams.begin()->second->ssrc;  // 复用已有 ssrc
} else {
    out_ssrc = allocate_ssrc();  // 新用户分配 ssrc
}

// 转发线程 (简化)：
while (running_) {
    received = recvfrom(sock, recv_buf, kBufSize, MSG_DONTWAIT, ...);
    auto* hdr = reinterpret_cast<RTPHeader*>(recv_buf);
    uint32_t ssrc = hdr->ssrc_val();
    // 根据 ssrc 找到 sender 的房间 + media_type
    // 遍历房间内其他参与者，按 media_type 转发
    for (auto& [uid, p] : participants) {
        if (uid == sender_id) continue;  // 不转发给自己
        sendto(sock, recv_buf, received, 0, &dest, sizeof(dest));
    }
}
```

### 为什么用 SFU 不用 MCU？

| 方案 | 特点 | 复杂度 |
|------|------|--------|
| **MCU**（Multipoint Control Unit） | 服务器**解码、合屏、重新编码** → 推一路流给客户端 | 高（需要完整音视频编解码器） |
| **SFU**（Selective Forwarding Unit） | 服务器**不解码，直接转发** UDP 包 | 低（纯转发，无编解码开销） |

SFU 服务器不必理解 RTP payload 内容（是 JPEG 还是 H.264 都不重要），**只解析 12 字节 RTP 头里的 ssrc** 就决定转发给谁。这大幅降低了中继服务器的 CPU 需求。

### 为什么用 ssrc 区分发送者？（`media_relay.cpp:248-254`）

RTP 包的 `ssrc` 字段（同步源标识）唯一标记一路媒体流。中继的全部逻辑就是：
1. 收到 UDP 包 → 读 `ssrc`
2. 查表：`ssrc → 房间 + media_type + 发送者`
3. 遍历房间内其他参与者 → `sendto` 转发

同一个用户的不同媒体类型（video/audio/screen）复用同一个 ssrc，保证了收端能用一个 ssrc 准确识别一个用户的所有媒体流。

**不用 ssrc 会怎样**：只能用 IP:端口对识别发送者，但多个客户端可能 NAT 到同一公网 IP，无法区分。

### 输入/输出

| | 数据 | 来源/去向 |
|--|------|----------|
| **输入** | UDP RTP 包（`recvfrom` 从客户端 UDP socket） | 客户端 `RtpSession::send_video_frame()` 发来的 JPEG 帧 |
| **输出** | 复制并转发给同一房间的其他客户端（`sendto`） | 其他客户端 UDP socket → `MediaEngine::on_rtp_packet_received` → `RemoteVideoWidget` |

## 八、MySQL 连接池 + RAII Guard

### 核心代码 (`connection_pool.h:45-58, connection_pool.cpp:34-81`)

```cpp
struct ConnGuard {
    MYSQL*          conn;
    ConnectionPool* pool;
    ~ConnGuard() { if (conn) pool->release(conn); }  // 析构自动归还
    ConnGuard(ConnGuard&& o) noexcept                 // 移动转移所有权
        : conn(o.conn), pool(o.pool) { o.conn = nullptr; }
    MYSQL* operator->() { return conn; }              // 像指针一样用
};

ConnGuard ConnectionPool::acquire() {
    std::unique_lock<std::mutex> lock(mutex_);
    cv_.wait(lock, [this] {
        return !idle_conns_.empty() || total_count_ < config_.max_connections;
    });
    MYSQL* conn = idle_conns_.empty() ? create_connection()  // 池空 → 新建
                                      : idle_conns_.front(); // 池有 → 取空闲
    return ConnGuard(conn, this);
}

void ConnectionPool::release(MYSQL* conn) {
    if (check_connection(conn)) {        // mysql_ping 检查是否健康
        idle_conns_.push_back(conn);     // 健康 → 回池
    } else {
        destroy_connection(conn);        // 不健康 → 销毁
    }
    cv_.notify_one();                    // 唤醒等待的 acquire()
}
```

### 为什么不用每次请求都新建 MySQL 连接？

MySQL 建立一次 TCP 连接 + 三次握手 + SSL/TLS 协商 + 权限验证，耗时 **5-50ms**。而连接池预创建 4 条连接（`min_connections=4`），`acquire()` 只是从空闲队列 `pop_front`——微秒级。

更重要的是，MySQL 连接数过多会耗尽服务器 `max_connections`（默认 151），新连接直接被拒绝。

**不用会怎样**：每次数据库操作都 `mysql_real_connect` → 查询 → `mysql_close`。查询本身可能只要 1ms，建连接却要 20ms——20 倍以上的连接建立开销。高并发时 MySQL 连接数瞬间打满，后续查询全部失败。

### ConnGuard RAII 设计

```cpp
// 使用方代码（user_repository.cpp）
auto result = [this](const std::string& email) -> std::optional<User> {
    ConnGuard guard = pool_.acquire();  // 获取连接，或阻塞等待
    // 用 guard-> 调用 mysql_xxx 函数
    mysql_stmt_prepare(guard->stmt, ...);
    // guard 析构 → 自动 release()，不需要 try-catch-finally
};
```

`ConnGuard` 析构函数自动调用 `release()`，即使中间抛出异常也能安全归还——C++ RAII 核心思想。

### 输入/输出

| | 数据 | 来源/去向 |
|--|------|----------|
| **输入** | `acquire()` 返回的 `MYSQL*` | 空闲池（`idle_conns_`）或新建（`mysql_real_connect`） |
| **输出** | `release()` 归还连接 | 送回空闲池或销毁 |

## 九、Qt 客户端跨线程安全（NetworkClient + 信号槽）

### 核心代码 (`network_client.h:31-35, network_client.cpp:13-24, main_window.cpp 消息处理`)

```cpp
// network_client.h — QObject 子类
class NetworkClient : public QObject {
    Q_OBJECT
signals:
    void connected();
    void message_received(const std::string& data);  // 网络线程发出信号
};

// main_window.cpp — UI 线程连接
connect(network_, &NetworkClient::message_received,
        this, &MainWindow::on_message_received);     // 默认 QueuedConnection
```

**关键点**：`NetworkClient` 作为 `QObject` 生活在主线程，但 `QTcpSocket::readyRead` 可以在任意线程触发（Qt 内部使用 select/epoll 事件循环）。信号槽是**队列连接**（`Qt::QueuedConnection`）——事件发送方线程把信号参数序列化后投递到接收方（UI 线程）的事件队列，UI 线程的 `QApplication::exec()` 循环在空闲时逐个执行。

### 为什么不用 `std::mutex` + 共享队列？

Qt 已经有完整的事件循环 + 线程安全的信号槽机制。如果在网络线程用 `mutex` 锁定 UI 控件，轻则 UI 卡顿，重则死锁（例如网络线程等 UI 线程释放锁、同时 UI 线程等网络线程发送数据）。

**信号槽队列连接**的方案：
- 网络线程：收到数据 → `emit message_received(data)` → 立即返回
- UI 线程：当前事件处理完 → 从事件队列取到 `message_received` 信号 → 执行槽函数

两者**完全不阻塞彼此**。

**不用会怎样**：要么跨线程直接操作 UI 控件导致崩溃（`QWidget` 不是线程安全的），要么加锁导致 UI 卡顿或死锁。

### 输入/输出

| | 数据 | 来源/去向 |
|--|------|----------|
| **输入** | `QTcpSocket::readyRead` 的原始字节流 | 服务端 TCP 响应的 Protobuf 数据 |
| **输出** | `emit message_received(body)` 信号 | UI 线程 `MainWindow::on_message_received` → switch 分发 |
| **输出** | 发往服务端的 Protobuf | `network_client.cpp:57-58` → `socket_->write(packet)` |

## 十、RAII / 智能指针

### RAII 示例：Socket (`tcp_connection.cpp:49-55`)

```cpp
// socket.h — RAII 封装
class Socket {
    ~Socket() { if (fd_ >= 0) ::close(fd_); }  // 析构自动关闭

    Socket(Socket&& other) noexcept             // 移动转移所有权
        : fd_(other.fd_) { other.fd_ = -1; }
};
```

Socket 的析构函数自动 `close(fd)`。即使构造函数中间抛出异常、或 `TcpConnection` 被意外销毁——socket 始终被正确关闭，不需要手动调用 `close`。

**不用会怎样**：忘记 `close(fd)` → fd 泄漏 → 进程 fd 达到 `ulimit -n`（通常 1024）→ 无法 accept 新连接。C 语言里这是最常见的线上故障之一。

### `shared_ptr` + `enable_shared_from_this` 生命周期

```cpp
// tcp_connection.cpp:23-26
void TcpConnection::start() {
    auto self = shared_from_this();  // 引用计数 +1
    loop_->add_read_event(sock_.fd(), [self]() {  // lambda 捕获 self
        self->handle_read();
    });  // lambda 析构时引用计数归还，但 epoll 持有 lambda = 仍持有 shared_ptr
}
```

此模式解决的核心问题：`TcpConnection` 的生命周期不由任何单一线程控制。它可能被：
- `TcpServer` 的连接表持有（`map` 中的 `shared_ptr`）
- epoll 回调 lambda 持有（`RunInLoop` 投递的闭包）
- `SignalingServer::on_message` 中临时持有（函数参数 `const shared_ptr<>&`）

只有所有这些持有者都放弃引用，对象才析构——**最后一个退出的人关门**。

## 十一、无锁 SPSC 队列

### 核心代码 (`lockfree_queue.h:19-106`)

```cpp
template <typename T>
class SPSCQueue {
    alignas(64) std::atomic<size_t> write_pos_;  // 缓存行对齐防伪共享
    alignas(64) std::atomic<size_t> read_pos_;

    bool try_push(const T& item) {
        size_t write = write_pos_.load(std::memory_order_relaxed);
        size_t next  = write + 1;
        if (next - read_pos_.load(std::memory_order_acquire) >= capacity_)
            return false;  // 队列满
        buffer_[write & mask_] = item;              // 写入数据
        write_pos_.store(next, std::memory_order_release);  // release：数据对消费者可见
        return true;
    }

    bool try_pop(T& item) {
        size_t read = read_pos_.load(std::memory_order_relaxed);
        if (read == write_pos_.load(std::memory_order_acquire))
            return false;  // 队列空
        item = buffer_[read & mask_];               // 读取数据
        read_pos_.store(read + 1, std::memory_order_release);  // release：槽位可复用
        return true;
    }
};
```

### 为什么能无锁？

**SPSC = Single Producer, Single Consumer**。只有生产者在写 `write_pos_`、只有消费者在读 `write_pos_`，两者不竞争同一原子变量，天然没有写-写竞争。读-读竞争（`read_pos_` 同理）。

对比 `std::queue + mutex`：每次 push/pop 都要 `lock_guard`，即使队列空/满也要获取锁——两条线程互相阻塞。

**不用会怎样**：音视频帧从采集线程 → 编码线程 → 网络线程，如果每帧都 `lock(mutex)` → `push` → `unlock` → `lock(mutex)` → `pop` → `unlock`，锁争用会吃掉 15-30% 的 CPU（实测数据），导致帧率下降。

### `alignas(64)` 缓存行对齐防伪共享

```cpp
alignas(64) std::atomic<size_t> write_pos_;  // 64 字节对齐 + 填充
alignas(64) std::atomic<size_t> read_pos_;   // 确保不同缓存行
```

现代 CPU 的 L1/L2 缓存行通常是 **64 字节**。如果不加 `alignas(64)`，`write_pos_` 和 `read_pos_` 可能落在同一缓存行。生产者更新 `write_pos_` 会使该缓存行失效（包括 `read_pos_`），消费者读 `read_pos_` 时必须重新从内存读——尽管消费者根本没用 `write_pos_`。这叫**伪共享（False Sharing）**，多核下性能会暴跌一个数量级。

### 输入/输出

| | 数据 | 来源/去向 |
|--|------|----------|
| **输入** | `try_push(item)` | 生产者线程（如采集线程） |
| **输出** | `try_pop(item)` → 消费 | 消费者线程（如网络发送线程） |

## 十二、三级 TLS 内存池

### 核心代码 (`memory_pool.h:27-89`)

```cpp
class MemoryPool {
    enum class Tier : uint8_t {
        SMALL  = 0,   // 8 KB  — 网络包头
        MEDIUM = 1,   // 64 KB — 业务消息体
        LARGE  = 2,   // 1 MB  — 媒体元数据
    };

    static thread_local ThreadLocalPool tls_pool_;  // 每线程独立池

    void* allocate(Tier tier) {
        auto* list = &tls_pool_.free_lists[static_cast<size_t>(tier)];
        if (!list->empty()) {                 // 池中有空闲块 → 直接复用
            void* ptr = list->back();
            list->pop_back();
            pool_hits_.fetch_add(1, std::memory_order_relaxed);
            return ptr;
        }
        return ::malloc(kBlockSizes[static_cast<size_t>(tier)]);  // 池空 → malloc
    }
};
```

### 为什么需要三级分档 + TLS？

**三级分档**：把高频分配按大小归到三个固定档位：
- 8KB：TCP 读写 Buffer 的初始分配
- 64KB：Protobuf 序列化出的业务消息（会议列表、聊天记录）
- 1MB：V4L2 帧缓冲区

每次 `malloc` 都要去堆管理器（ptmalloc/jemalloc/tcmalloc）里找合适的内存块——涉及锁（arena 锁）、空闲链表遍历、系统调用（brk/mmap）。固定档位优先从 `thread_local` 的无锁空闲链表取，0 次系统调用、0 次锁操作。

**TLS（`thread_local`）**：每个线程有自己的空闲链表，**完全无锁**。线程退出时 TLS 池析构，调用 `free` 归还所有块。

**不用会怎样**：音视频帧每秒 25 帧，每帧 200KB JPEG，频繁 `malloc/free` 导致：
- 内存碎片（物理内存够但分配不出连续大块）
- 锁争用（全局 `malloc` 锁）
- 系统调用开销（`brk`/`munmap`，约 2-5μs 每次）

### 输入/输出

| | 数据 | 来源/去向 |
|--|------|----------|
| **输入** | `allocate(Tier)` | Buffer 构造、V4L2 帧缓冲、Protobuf 序列化 |
| **输出** | `deallocate(ptr, Tier)` | Buffer 析构、帧处理完毕、序列化结束 |
| **命中** | 池中取（微秒级）→ 返回已有块 | 池空时 → `malloc`（微秒级+） |
